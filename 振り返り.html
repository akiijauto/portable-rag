振り返り：ローカルRAG 開発（2026-09-02）

1. 取り組みの要約

「API 不可・ドライブのみ・インストール不要」という制約を、標準ライブラリだけで満たす RAG 検索を作った。BM25 転置索引を SQLite に持ち、意味検索はライブラリがある時だけ自動で有効になる二段構えにした。5,000件の合成データで構築 33秒・検索 0.4秒を確認。

2. 起きた課題と解決

#課題原因解決学び
1タイトルが取れず本文の先頭行が使われたHTML パーサで head タグを丸ごと読み飛ばしていたため title も消えていた読み飛ばし対象から head を外し、script/style/noscript だけを除外「余計なものを除外する」処理は、除外しすぎを必ずテストで確認する
2Web UI がスレッドエラーで落ちたSQLite 接続をメインスレッドで作り、リクエスト処理スレッドから使ったcheck_same_thread=False にし、サーバーも単一スレッドの HTTPServer へ変更ローカル1人用ツールは並列化しない方が単純で堅い
3ブラウザで検索ボタンを押しても結果が出ないJS で要素を top・status という id で参照していたが、これは window.top／window.status という予約済み名前で衝突したdocument.getElementById 経由に統一id をそのまま変数として使わない。ブラウザ実行テストで初めて発覚した種類のバグ
4テストの期待件数が合わない英語文書は日本語クエリにヒットしないので当然の結果だった期待値を固定数ではなくヒット数に連動させたテストは「仕様」を書く。実装の都合で数を決め打ちしない
5索引ファイルが 197MB と大きめbigram の転置索引を SQLite の行で持つため用語文字列が重複保存される今回は許容（5,000件で十分動く）。将来は用語 ID 化や postings の圧縮で 1/3 程度にできるまず動くものを出し、規模が増えたら最適化する

2-3. 追加開発：検索対象フォルダの画面設定と一致度の表示

課題原因解決学び
検索対象フォルダをどこで指定するのか分からない（ユーザー指摘）指定手段が config.json の手編集しかなく、検索画面にもコントロールUIにも欄が無かった。初心者に JSON をメモ帳で書かせる前提になっていたコントロールUI（launcher.py）に「検索対象フォルダ」欄を追加。「参照」でフォルダを辿って選び、フォルダごとに対象ファイル数を表示する。書き換えるのは同じ config.json の source_dirs だけで、他の項目は触らない「設定ファイルを直せば動く」は開発者の感覚。使う人が最初に触る画面に、最初に決めるべき項目を置く。件数を出すと「フォルダを間違えた」にその場で気づける
検索結果の「スコア」がどのクエリでも同じ値（1位=0.01639, 2位=0.01613…）表示していたのは RRF の融合値で、ベクトル検索が無い環境では順位だけで決まる固定値になる。当たっているか外れているかがスコアから読めないTSV と HTML に BM25 の生スコアを一致度として出す（意味検索が有効なら意味的な近さも併記）。TSV は5列→6列実データ5,000件では「一応ヒットしたが的外れ」が必ず混ざる。それを人が見分けられる数字を出しておく。サンプル6件では気づけない種類の問題

2-4. 追加開発：系列まとめのブラウザ画面版（bundle_app.py）

課題原因解決学び
「系列まとめが黒い窓で分かりづらい」（ユーザー指摘）番号を打って答える対話メニューは、選択肢の意味も、実行したら何ができるのかも、実行前には分からない。誤って Enter を押すと既定で走るブラウザ画面版を追加。①分け方を4つのカードから選ぶ → 「分け方を確認」でグループ数と件数を実行前に表示 → ②作るものにチェック → ③「まとめを作る」→ 結果の表・「次にやること」・「フォルダを開く」ボタン。正規表現は「区切り文字を選ぶ」に置き換え、詳しい人向けに折りたたみで残した。処理本体は bundle.py をそのまま呼ぶ初心者向けUIの要点は「押す前に結果が想像できる」「押した後に次の一手が書いてある」の2つ。既存の CLI は壊さず、画面は薄い層として被せる
旧ボタン設定（launcher.json）が bundle.py を指したまま残るlauncher.json は git 管理外で、配布先ごとに残るlauncher.py 読み込み時に、同じ場所へ bundle_app.py があれば自動で差し替える設定ファイルが利用者側に残る前提で、移行は読み込み側で吸収する

残っていたものなぜ問題か対応

rag/__pycache__/*.pyc 9件ソースの旧パスが埋まり、トレースバックが旧パスで出る削除（次回実行で再生成）

2-6. 索引作成が10倍遅かった原因は Google ドライブ同期（2026-09-03）

業務PCで実データ100件の索引作成に400秒かかった。原因は索引フォルダが Google ドライブの同期対象配下にあったこと。同期外のフォルダへ移しただけで42秒になった。約9.5倍。

rag/config.py には以前から「インデックスの保存先（ローカル。ドライブ同期外に置くと速い）」と書いてあったが、効果の大きさを数値で書いていなかったため読み飛ばされた。書き込みは1回の構築で数百万行に及ぶので、同期対象だと1行ごとにファイル変更が検知されて桁が変わる。

「HTML を Markdown に変換すれば速くなるか」も検討したが、開発機での段階別実測で否定された。同じ内容の100件・1件867KB・45,502チャンクで比較した結果。

段階HTML のままMarkdown 変換済み

HTML 解析9.43s0.41s
チャンク分割0.70s0.77s
トークン化4.46s4.11s

HTML 解析は全体の約10%しかなく、Markdown 化しても14.8%しか縮まない。支配的なのは SQLite への書き込みで8割超。転置索引に索引が張られた状態で2,280万行を挿入しているため、1行ごとに B 木の再構成が起きる。書き込み方式だけを変えて測った結果は次のとおり。

2-7. 「途中から急に遅くなる」は誤読だった。所要はチャンク数でほぼ決まる（2026-09-03）

進捗表示を10件ごとにしたところ、業務PCで所要が跳ね上がる回が現れた（1,070→1,080件で236秒、その後21秒に戻る回もあり）。これを見て「索引が育ってキャッシュに載らなくなった崖」だと断定したが、誤りだった。ユーザーから「規則性がない秒増減なので元のデータ量では」と指摘され、測り直して否定された。

サイズがばらつく合成HTML 300件・103MB（本文2KB〜2,930KB、中央値35KB）を、10件ごとに「所要・チャンク数・索引の行数」を記録しながら構築した。

指標キャッシュ 2MBキャッシュ 256MB
合計128秒61秒
所要 と そのバッチのチャンク数 の相関+0.982+0.991
所要 と 索引の大きさ の相関+0.233+0.149
秒/千チャンク（前半5回 → 後半5回）1.60 → 2.120.84 → 1.06

秒の増減は、そのバッチに入っていたデータ量でほぼ全部説明できる。実際、8,051チャンク入った回は7.0秒、868チャンクの回は0.9秒で、秒/千チャンクはどちらも0.9。索引が育つことによる悪化は1,333万行の範囲で26〜33%にとどまり、崖は存在しない。

したがってキャッシュ拡大は「崖の解消」ではなく、最初から最後まで効く約2.1倍の定数倍改善だった。効果自体は本物なので設定は残す。ただし説明が違う。

対策として進捗ログを変更した。件数だけでなくチャンク数・MB・秒/千チャンクを出す。件数だけ見ると不規則に見えるものが、チャンク数を並べると一定になる。

  220 件処理  直近10件: 8,051 チャンク 12.5MB 7.0s (0.9秒/千チャンク)  累計 44s
  240 件処理  直近10件: 868 チャンク 1.3MB 0.9s (1.0秒/千チャンク)  累計 47s

学び：進捗ログの跳ね上がりという観測から「キャッシュ不足の崖」という機序へ1段で飛んだ。キャッシュの効果自体は対照実験（同じ10件・同じ索引で9.1秒対3.1秒）で確かめてあったので、その数字を根拠に別の主張まで通してしまった。測ったのは「キャッシュを変えると速くなる」であって、「あのログの形の原因がキャッシュだ」ではない。正しい切り分けは、所要をチャンク数で割って正規化すること。CLAUDE.md の「説明がきれいに通ることは、確からしさではない」に該当する事例。
実装した対策の評価（訂正後）：キャッシュ拡大は約2.1倍の定数倍改善で有効。用語 ID 化は1.16倍と索引サイズ85%で穏当。同期フォルダ警告（2-6）だけが桁で効く対策で、これは実測9.5倍の裏づけがある。

2-8. 「動いているのか止まっているのか分からない」を直す（2026-09-03 ユーザー要望）

要望は2つ。①ボタンを押したあとの状態が分からない ②終了ボタンでコマンドラインの窓ごと片付けたい。

①の原因は設計にあった。3つの画面（rag_app / launcher / bundle_app）はいずれも単一スレッドの HTTPServer で、索引更新をリクエストの中で最後まで実行していた。その間サーバーは他の要求に一切応答できないので、進捗を問い合わせる余地が原理的に無かった。5,000件なら30分以上、画面は「更新中…」のまま固まる。

変更内容
rag/webui.py を追加ThreadingHTTPServer ＋ Job（背後で実行し進捗を保持）＋ request_shutdown
索引更新を投げっぱなしに/api/reindex は即座に返し、画面は /api/progress を0.7秒ごとに見る
生存の可視化点滅する丸、経過秒、最後に応答があった時刻を出す。応答が途切れたら「応答がありません」と明示する
検索にも経過秒0.1秒ごとに更新。無反応との区別がつく
終了ボタン3画面すべてに追加。確認したうえで /api/exit → サーバー停止 → 終了コード0
.bat の pause正常終了（0）なら窓を閉じる。エラー時だけ止めて内容を読ませる

実測での確認: 300件の索引更新中に進捗行が0→33行まで増え、更新中に検索も実行できた（ヒット3件）。二重起動は拒否される。3画面とも終了コード0で停止することを確認。

設計上の要点：shutdown() は serve_forever() と同じスレッドから呼ぶと止まらないため、別スレッドからわずかに遅らせて呼ぶ。遅らせるのはブラウザへ応答を返し切ってから止めるため。
「生きている」ことの示し方：進捗の行が増えなくても、/api/progress が応答すること自体が生存の証拠になる。だから snapshot は running でなくても必ず返る設計にし、画面には最終応答時刻を出している。大きい文書1件に時間がかかって行が増えない間も、無音の秒数を出して「処理中」と分かるようにした。
窓が閉じない原因は pause だった。プログラム側をいくら直しても、.bat が常に pause していれば窓は残る。終了コードで正常と異常を伝え、.bat 側で分岐させるのが要点。

3. 判断した設計方針

  • 形態素解析器を使わない。辞書インストールが要るため制約に反する。文字 bigram で「返品／送料／負担」のような業務語は十分に当たる。
  • AI 本体を含めない。回答生成は Gemini やスプレッドシートに任せ、このツールは「根拠を探して整える」役に徹する。制約の中で最も価値が出る分担。
  • 索引は git に入れない。機密を含むため .gitignore で除外。コードだけをリポジトリで管理する。
  • 意味検索は「あれば使う」。pip 可の PC では効果を試せ、不可の PC でも同じコードが動く。
